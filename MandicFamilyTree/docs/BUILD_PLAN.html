Build plan · Dynamic Family Tree Webapp

From static mockup to working app

An audit of what exists today in MandicFamilyTree, and a phased plan to finish the frontend, build the backend, and wire it together.

Stack: Node.js + Express + TypeScript + SQLite Hosting: AWS EC2 Auth: multi-user accounts

00Where things stand today

The project is a Vite + React 19 + TypeScript frontend with no backend of any kind. Everything is a static, hardcoded dataset bundled at build time — there's no API, no database, no authentication, and nothing that survives a page reload. Below is a page-by-page and component-by-component read of what's actually there.

Data layer

All "data" lives in two hardcoded TypeScript files: src/data/mockDatabase.tsx defines the Person type and a buildPersonNode() function that nests a flat array into a tree by offspringUid; src/data/bigDatabase.tsx holds 176 generated fake "Sinclair" family records (produced offline by script.py and pasted in by hand). There's a circular import between the two files that happens to work but is worth cleaning up.

Confirmed with a full grep of src/: zero instances of fetch, axios, localStorage, or any network/persistence call. Reloading the page always resets to the exact same 176 fake people. Nothing a user does in the UI survives a refresh.

Other loose ends

  • Chakra UI is a declared dependency but never actually imported — dead weight in the bundle.
  • misc/ (List.tsx, functions.ts, types.ts) are personal TypeScript practice files, unrelated to the app and unused.
  • src/components/Untitled-1.ini is an unrelated stray text file (looks like a pasted network-debugging log) sitting in the components folder — safe to delete.
  • script.py is a working, seeded Python generator for fake family data — useful to keep around for future test datasets, but it's a standalone script, not part of the build.
  • No .env, no server//api/ folder, no backend dependencies in package.json at all. This is a 100% static frontend today.
Bottom line: the visual shell and the tree-drawing concept are there, but almost nothing is actually wired up — not even within the frontend (buttons that don't do anything, forms that don't submit anywhere, photos that never change). The profile page doesn't exist, and there is no backend whatsoever. This plan treats the current frontend as a prototype to harden, not a finished layer to build an API under.

01Target shape of the system

Per your answers: a Node.js + Express + TypeScript API, backed by SQLite, with real per-user accounts (so multiple family members can log in individually, with roles distinguishing who can edit vs. just view), deployed on an AWS EC2 instance. The frontend stays React + Vite, now talking to the API instead of importing static files.

Proposed repo layout

MandicFamilyTree/
  src/                  (existing React frontend)
  server/               (new) Express + TS API
    src/
      db/               SQLite connection, migrations, seed script
      models/           typed data-access functions per entity
      routes/           people, relationships, auth, media
      middleware/       auth guard, role guard, error handler
      index.ts
    package.json        (separate from frontend, or a workspace)
  shared/               (optional) types shared between client & server

A separate server/ package keeps frontend and backend dependency trees independent, which matters once you deploy — the EC2 box only needs to run the server (serving the built frontend as static files, or behind nginx).

Data model — moving off array-of-ids

The current Person type stores relationships as bare id arrays (parentUid: number[], spouseUid?: number[], offspringUid: number[]) duplicated on every related person — e.g. a child's uid appears in both parents' offspringUid arrays, and nothing enforces that those stay in sync. That's fine for a hand-edited mock file; it's a liability once people can add/edit through a UI, because it's easy for the arrays to drift out of sync with each other. For the real database, normalize into tables:

proposed SQLite schema (simplified)
TableColumns
peopleid, first_name, last_name, maiden_name, gender, date_of_birth, date_of_death, residency, note, profile_pic_url, created_by, created_at, updated_at
relationshipsid, person_a_id, person_b_id, type (parent_of / spouse_of), start_date (for marriages), end_date
usersid, email, password_hash, display_name, role (admin / editor / viewer), linked_person_id (nullable — ties a login to their own tree entry), created_at
mediaid, person_id, file_url, kind (photo / document), caption, uploaded_by, created_at
sessions (optional)only needed if you go with server-side sessions instead of JWT — see open decisions below

A parent_of relationship row from A → B means "A is a parent of B"; siblings and spouses fall out of querying this one table, and children/parents/spouses can be derived with simple joins instead of trusting arrays to stay consistent. The API can still shape responses into the existing PersonNode tree format the frontend already expects, so this change is invisible to react-d3-tree.

02Phased plan

Nine phases, roughly in dependency order. Each is small enough to ship and test on its own rather than one giant rewrite.

Phase 0

Clean up the frontend prototype

Cheap wins that remove noise before building on top of this code.

  • Delete dead files: Button.tsx, Scripts.tsx, CustomPathFn.tsx (or wire it in, if you like the organic branch look), UserGreating.tsx, misc/, Untitled-1.ini, the unused DatabaseOld / DatabaseMediumFlat / commented-out DatabaseFlat blocks.
  • Remove @chakra-ui/react from package.json if you don't intend to adopt it, or commit to using it for the remaining UI work.
  • Strip stray top-level console.logs that fire on module import (mockDatabase.tsx) and the debug logs inside FamTree.tsx.
  • Fix the curentDepth typo and the invalid type="firstName"-style input attributes in AddUser.tsx while you're in those files.
Phase 1

Backend foundations

Nothing else can be wired up until there's an API to wire to.

  • Scaffold server/: Express + TypeScript, better-sqlite3 (synchronous, simplest for a small personal-scale app) or sqlite3/knex if you want a query builder.
  • Write migrations for people, relationships, users, media.
  • Write a seed script that imports the existing DatabaseBigFlat data (converted into the new schema) so you have real data to develop against immediately.
  • Basic Express setup: JSON body parsing, CORS (for local dev against Vite's port), centralized error handler, request logging.
Phase 2

Authentication & roles

You asked for real multi-user accounts, not a shared login — this has to exist before any write endpoint matters.

  • Signup / login endpoints; hash passwords with bcrypt; issue JWTs (or sessions — see open decision below).
  • Auth middleware that attaches the current user to each request; role-guard middleware for write operations (e.g. only editor/admin can create or modify people).
  • Build out Login.tsx for real: actual form, calls the API, stores the token, redirects on success, shows errors on failure.
  • Add a basic "my account" affordance (who's logged in, log out) — this is where the never-used UserGreating component idea finally gets a real purpose.
Phase 3

Core people/relationships API

CRUD for the actual domain data.

  • GET /people, GET /people/:id, POST /people, PATCH /people/:id, DELETE /people/:id (soft-delete recommended for a family archive — don't actually lose history).
  • POST /relationships, DELETE /relationships/:id for linking parents/spouses.
  • GET /tree/:rootId — server-side endpoint that walks the relationships table and returns a pre-built PersonNode-shaped tree, so the frontend doesn't need its own tree-building logic duplicated against a new data shape.
  • Input validation (e.g. zod) on every write endpoint.
Phase 4

Media (photos & documents)

Right now every person shows the identical placeholder photo — fixing that needs real upload/storage, not just a data field.

  • POST /people/:id/media — multipart upload endpoint, storing files either on local disk on the EC2 instance (simplest) or S3 (more durable, barely more work if you're already on AWS).
  • Serve uploaded images statically; update PersonCard/Crest/CustomNode to actually read each person's profilePic URL instead of the hardcoded placeholder import.
Phase 5

Wire the frontend to the API

Replace static imports with real data fetching everywhere.

  • Add a small API client (fetch wrapper) and a data-fetching layer — plain useEffect+state is fine at this scale, or @tanstack/react-query if you want caching/refetch handled for you.
  • Replace every import of Database2 / DatabaseBigFlat in Home.tsx, Overview.tsx, FamTree.tsx with calls to the new endpoints.
  • Make AddUser.tsx actually functional: controlled inputs, real onSubmit that POSTs to /people, success/error feedback, and a refresh of whichever view is open.
  • Fix the DOM-manipulation patterns in SwitchTreeViewButton.tsx, Header.tsx, and Home.tsx's tree-view toggle to use React state (useState/context) instead of getElementById/getElementsByClassName — this will also make the app much easier to extend going forward.
Phase 6

Build the person profile page

This is currently a 0-byte file and a commented-out route — the single largest missing piece.

  • Re-enable /profile/:id in App.tsx.
  • Build PersonProfile.tsx from scratch: full bio fields, dates, residency, note, relationship list (parents/spouse/children, each linking to their own profile), photo gallery, and edit controls (gated by role).
  • Wire Overview.tsx's grid and the tree's CustomNode clicks to navigate to a person's profile.
  • Give SideBar.tsx and Toolbar.tsx a real job — e.g. hovering a tree node populates the sidebar with a quick-view card instead of static placeholder text.
Phase 7

Fix the tree rendering itself

Both tree implementations currently have real correctness bugs, independent of the data-source change.

  • Decide on one tree renderer: either commit to react-d3-tree (used in Home.tsx) or FamTree.tsx's treeflex approach — maintaining both long-term is wasted effort.
  • If keeping FamTree.tsx: make it recursive and lookup-by-uid instead of hardcoded array index, and relax the "both parents must exist" requirement so people with only one known parent still render.
  • Decide how to handle multiple marriages/remarriage and unknown ancestors (the current data uses sentinel uid: 999/998 "unknown" placeholder people — fine as a convention, but worth making explicit/documented rather than implicit).
Phase 8

Deploy to EC2

Your target environment — plan for it rather than bolting it on at the end.

  • Single EC2 instance running: Node process (API, via pm2 or a systemd service) + nginx reverse proxy serving the built React app and proxying /api/* to Express + HTTPS via Let's Encrypt/Certbot.
  • SQLite file lives on the instance's disk — back it up (a simple cron'd copy to S3 is enough at this scale; SQLite doesn't need a managed DB service for a family-sized dataset).
  • Environment config via .env (JWT secret, port, upload path) — never commit secrets; use an EC2-scoped .env or AWS Secrets Manager if you want to be thorough.
  • Basic CI (even just a GitHub Action that runs tsc + lint on push) catches regressions before they reach the instance.
Phase 9

Polish & hardening

Last, once the app actually works end-to-end.

  • Loading/error states on every data fetch (currently nothing handles a failed/slow request anywhere).
  • Basic responsive pass — nothing in the current CSS modules appears to target phone widths.
  • Simple automated tests for the relationship-walking logic (easy to get subtly wrong) and for the auth/role guards.
  • A real gallery generator for Toolbar.tsx (currently a hardcoded placeholder set with a TODO comment acknowledging it was never built).

03Open decisions worth settling early

JWT vs. server-side sessions
JWTs are simpler to deploy (stateless, no session store) and fine for a small family app; sessions are easier to revoke instantly if someone's access needs to be cut off. For this scale, JWT with a reasonably short expiry + refresh token is the pragmatic default unless you specifically want instant revocation.
Photo storage: local disk vs. S3
Local disk on the EC2 instance is simplest to start and costs nothing extra; S3 survives an instance replacement/resize and is barely more code since you're already on AWS. Worth doing S3 from the start if you expect to resize/replace the instance later.
Invite-only vs. open signup
For a family tree, you almost certainly want admin-issued invites rather than public signup — worth deciding before building the signup flow so you don't build the wrong one.
One tree renderer, not two
Phase 7 above — pick react-d3-tree or the treeflex/FamTree approach rather than maintaining both indefinitely.

04Suggested order to actually work in

Phases 0 → 1 → 2 → 3 unlock everything else and are mostly backend-only, so they can proceed without touching the fragile frontend bits yet. Phase 5 (wiring) is the one that touches the most existing files at once — doing phases 0 and 7 first means you're not wiring broken logic to a real API. Phases 4, 6, and 9 can interleave once the API is stable; phase 8 (EC2 deploy) is worth doing once, early, even with a half-finished app, just to deploy a known process rather than leaving it until the end.
